Administrator Guide

Configure & Operate the Agent-Intake Gate

A self-guided walkthrough for M365 and Power Platform administrators. By the end you will have a pilot-ready configured agent intake pipeline — from Dataverse schema to classification zones, reviewer queues, and retention records. This solution is v1.0.0-preview: suitable for pilot validation, not broad production rollout without customer governance sign-off.

Self-guided FINRA 3110 / 4511 SEC Rule 17a-4 OCC 2011-12 / SR 11-7 GLBA 501(b)

By the end of this guide you will:

  • Deploy the 9-table Dataverse schema and solution shell
  • Bind the four standard connection references (plus the optional Graph reference) inside the FSIAgentIntake solution
  • Populate the 7 environment variables and classify agent request paths
  • Set up reviewer roles, the Purview retention label, and Entra Agent ID minting
  • Monitor the intake pipeline and read the fsi_intakedecisionlog audit trail

Step 1

Prerequisites

Gather these resources before running any scripts. Missing one will stall the deployment mid-flight.

Power Platform environment

  • A Sandbox or Production environment with Dataverse enabled.
  • Your environment must allow custom solutions (unmanaged) — confirm in the Power Platform admin center under Settings > Product > Features.
  • Use -AllowedEnvironmentType Sandbox to restrict accidental Production deploys.

Licenses

  • Power Apps Premium — required for each maker who submits an intake request (model-driven app).
  • Power Automate Premium — required for the account running automated flows (HTTP, Dataverse triggers).
  • Microsoft Teams — required for sponsor and reviewer adaptive-card delivery.

Administrator roles

  • Power Platform Administrator or Environment Admin — to deploy solutions, create env vars, and bind connection references.
  • Entra Global Administrator or Privileged Role Administrator — to grant admin consent for the Graph application permissions (AgentIdentity.CreateAsManager or AgentIdentity.Create.All).
  • Compliance Administrator (Microsoft Purview) — to create and publish the retention label FSI-AgentIntake-7yr.

Toolchain (local workstation)

Install these before running any deployment scripts:

# PowerShell modules (run as administrator)
Install-Module -Name Az.Accounts          -MinimumVersion 2.0.0  -Scope CurrentUser -Force
Install-Module -Name powershell-yaml      -MinimumVersion 0.4.0  -Scope CurrentUser -Force
# Exchange Online is only needed if you are NOT passing -SkipPurviewLabel
Install-Module -Name ExchangeOnlineManagement -MinimumVersion 3.2.0 -Scope CurrentUser -Force

# Power Platform CLI
winget install Microsoft.PowerApps.CLI   # or: msiexec /i PowerAppsCLI.msi

# Python 3.10+ (for Agent Identity blueprint script)
python --version   # verify 3.10 or later

Purview label shortcut

If your Purview retention label (FSI-AgentIntake-7yr) already exists or will be created separately, add -SkipPurviewLabel to the deploy call. This also removes the ExchangeOnlineManagement module requirement for that run.

Standard connectors needed

  • Microsoft Dataverse — reads and writes intake records.
  • Microsoft Teams — delivers sponsor and reviewer adaptive cards.
  • Office 365 Outlook — sends email reminders and escalation fallbacks.
  • HTTP with Microsoft Entra ID — authenticates calls to the classifier API, MRM system, and drift detector.
  • Microsoft Graph custom connector (optional) — prefills maker profile data and performs Agent ID actions. The deploy scripts add this reference only when you supply the custom connector; otherwise they emit a manual step for the Graph lookup.

Pre-create connections under your service account in Power Apps > Connections before running the solution shell script. The script binds existing connections — it does not create them.

Step 2

Deploy the Solution Shell

Two scripts do the heavy lifting: provision_solution_shell.ps1 (quick start) or deploy.ps1 (full control with all options). Both are idempotent — safe to re-run.

Option A — Provision script (recommended first-time)

pwsh .\scripts\provision_solution_shell.ps1 `
  -EnvironmentUrl  "https://<org>.crm.dynamics.com" `
  -EnvVarValues @{
    fsi_intake_powerplatformenvironmenturl = "https://<org>.crm.dynamics.com"
    fsi_intake_makerportalurl              = "https://<org>.crm.dynamics.com/main.aspx?appid=<id>"
    fsi_intake_reviewerappurl              = "https://<org>.crm.dynamics.com/main.aspx?appid=<reviewer-id>"
    fsi_intake_mrmtargetenv                = "https://<mrm-env>.crm.dynamics.com"
    fsi_intake_driftdetectorenv            = "https://<drift-env>.crm.dynamics.com"
    fsi_intake_retentionlabelid            = "<purview-label-guid-or-name>"
    fsi_intake_sponsorbackupgroup          = "sg-agent-intake-sponsors@contoso.com"
  }

Option B — Full deploy.ps1 (all environments / CI)

# Minimal required — prompts for credentials interactively
pwsh .\scripts\deploy.ps1 -EnvironmentUrl "https://<org>.crm.dynamics.com"

# Typical CI invocation with managed identity
pwsh .\scripts\deploy.ps1 `
  -EnvironmentUrl   "https://<org>.crm.dynamics.com" `
  -AuthMode         ManagedIdentity `
  -SkipPurviewLabel `
  -LogPath          ".\logs\deploy-$(Get-Date -Format yyyyMMdd-HHmm).log"

# Validate without making changes (dry run)
pwsh .\scripts\deploy.ps1 `
  -EnvironmentUrl   "https://<org>.crm.dynamics.com" `
  -DryRun

deploy.ps1 switches at a glance

-EnvironmentUrl (required) — Dataverse org URL.
-AuthMode — AzCli (default), ManagedIdentity, or ServicePrincipal.
-DryRun — log every step without making changes.
-SeedTestData — load 5 deterministic smoke scenarios.
-SkipSmoke — skip the smoke-test step.
-SkipPurviewLabel — skip Purview label creation (removes ExchangeOnline dependency).
-Teardown — remove the solution from the environment (destructive).
-BillingPolicyId — attach a pay-as-you-go billing policy.
-LogPath — path for the structured JSON log file.

What the deployment creates

The 8-stage deploy pipeline provisions the following:

  • 1

    Dataverse schema (9 tables)

    Publisher FSIPublisher — prefix fsi_. The nine tables are fsi_intakerequest, fsi_intakedatasource, fsi_intakerisksignal, fsi_intakereview, fsi_intakeapproval, fsi_intakedecisionlog, fsi_intakesponsorship, fsi_intakeauditevent, and fsi_intakeretentionrecord. Zone values come from the fsi_acv_zone option set — not a table.

  • 2

    Unmanaged solution: FSIAgentIntake

    The outer container for all components. Subsequent steps place connection references, environment variable definitions, and app components inside this solution.

  • 3

    Model-driven app (reviewer queue)

    The intake reviewer model-driven app is provisioned inside FSIAgentIntake. Record its app ID — you will need it for the fsi_intake_reviewerappurl environment variable.

  • 4

    Environment variable definitions (7)

    Definitions are created; values must be set separately (see Step 5). This separation allows the same solution package to be moved between environments without embedding environment-specific values.

  • 5

    Connection reference stubs (four standard + one optional Graph)

    Logical placeholders (fsi_cr_dataverse_agentintake, fsi_cr_teams_agentintake, etc.) are registered inside FSIAgentIntake. The deploy scripts define and validate four standard references — Dataverse, Teams, Office 365 Outlook, and HTTP with Microsoft Entra ID — plus the optional Microsoft Graph reference (added only when the custom connector is supplied, otherwise left as a manual step). You bind actual connections in the next step.

  • 6

    Identity and security roles

    Custom Dataverse security roles for reviewers, makers, and the automation service account are created and scoped to the solution.

  • 7

    Purview retention-label hydration

    Unless -SkipPurviewLabel is passed, the script creates and publishes FSI-AgentIntake-7yr via Exchange Online PowerShell. The resulting GUID populates fsi_intake_retentionlabelid.

  • 8

    Optional seed data + smoke test

    With -SeedTestData: five deterministic intake scenarios (Express-happy, Standard-conditional, Full-parallel-board, cross-border-deny, sponsor-self-approval-deny) are loaded. Then pwsh scripts/smoke_test.ps1 validates end-to-end flow execution.

Step 3

Create & Bind the Connections

The FSIAgentIntake solution ships with four standard connection reference stubs — Dataverse, Teams, Office 365 Outlook, and HTTP with Microsoft Entra ID — plus an optional Microsoft Graph reference. You bind pre-existing connections to these stubs; you do not create new references.

Critical — do not click “+ New connection reference”

Creating a new reference in the designer generates a different logical name (e.g., fsi_dataverseagentintake). Flows and scripts reference the original names (e.g., fsi_cr_dataverse_agentintake). The duplicate sits in the Default solution and is never used — binding it does nothing. Always bind the references that already exist inside Solutions > FSI Agent Intake > Connection references.

Step 3a — Pre-create connections

In Power Apps > Connections, create one connection per connector under your service account. You need connections for: Microsoft Dataverse, Microsoft Teams, Office 365 Outlook, HTTP with Microsoft Entra ID, and the Microsoft Graph custom connector.

Step 3b — Bind each reference to a connection

Open Power Apps > Solutions > FSI Agent Intake > Connection references. For each reference below, select it and choose Edit to bind it to the matching connection you pre-created in Step 3a. Bind the four standard references; bind the optional Graph reference only if you created the Graph custom connector.

Logical name: fsi_cr_dataverse_agentintake

Connector: Microsoft Dataverse

Used by: All flows that read or write fsi_intakerequest, fsi_intakedecisionlog, and related tables.

Account: Use a service account with the System Customizer or solution-specific Dataverse security role.

Logical name: fsi_cr_teams_agentintake

Connector: Microsoft Teams

Used by: Sponsor 1-click approval card, reviewer decision cards, and escalation notifications.

Account: Service account with a Teams licence. Cards are posted on behalf of this account.

Logical name: fsi_cr_office365_agentintake

Connector: Office 365 Outlook

Used by: Reviewer reminder emails, sponsor escalation fallback when Teams delivery is unavailable, overdue-review notifications.

Account: A shared mailbox or service account with a licensed Exchange Online mailbox.

Logical name: fsi_cr_http_agentintake

Connector: HTTP with Microsoft Entra ID

Used by: Automated classification API calls, Model Risk Management handoff, drift-detector handoff at end of Standard and Full intake paths.

Account: Requires an Entra app registration with delegated or application permissions scoped to the classifier and MRM endpoints.

Logical name: fsi_cr_graph_agentintake

Connector: Microsoft Graph custom connector (optional — added only when the custom connector is supplied; otherwise a manual step)

Used by: Maker profile auto-fill on the intake form, Entra Agent ID minting on approval (Express, Standard, and Full), and Agent Identity blueprint hydration.

Account: Requires admin consent for AgentIdentity.CreateAsManager or AgentIdentity.Create.All Graph application permissions.

Troubleshooting — references missing from the solution

Recovery: reference is in Default solution, not FSIAgentIntake

Symptom: the reference exists in the environment but is missing from Solutions > FSI Agent Intake > Connection references.
Recovery: look up the connection reference ID in the Default solution, then run:
pac solution add-solution-component --solutionUniqueName FSIAgentIntake --component <id> --componentType connectionreference
Pass the component type by its name connectionreference — the numeric codes 371 and 10137 are rejected with "not known, Please provide the Component Type name".

Step 4

Populate the Environment Variables

Seven environment variables control where the intake pipeline sends records, notifications, and handoffs. Set them in Solutions > FSI Agent Intake > Environment variables or pass them to the provision script (see Step 2).

Current value vs. default value

Dataverse stores two rows per variable: the definition (default, ships with the solution) and the optional current value override. Always set a current value — do not edit the default, as that would be overwritten on the next solution import.

Schema name What to set Notes
fsi_intake_powerplatformenvironmenturl Dataverse org URL, e.g. https://contoso.crm.dynamics.com Used by flows to construct OData requests against fsi_intakerequest and related tables.
fsi_intake_makerportalurl Full URL of the public-facing maker intake portal page Shared with makers in notification emails and Teams messages. Typically the model-driven app URL for the maker-facing form.
fsi_intake_reviewerappurl Full URL of the reviewer model-driven app Included in reviewer notification cards so approvers can open the queue directly. Record the app ID from the deploy output.
fsi_intake_mrmtargetenv Model Risk Management environment URL or wrapper endpoint The Full intake path posts a handoff payload here after board approval when MRM criteria are met (OCC 2011-12 / SR 11-7).
fsi_intake_driftdetectorenv Drift-detector environment URL or wrapper endpoint Receives a post-approval scope signal so drift detection can be seeded from intake data. May point to the same or a separate environment.
fsi_intake_retentionlabelid Purview retention label GUID or the label name FSI-AgentIntake-7yr Applied to fsi_intakeretentionrecord rows to support a 7-year retention class. Helps meet FINRA Rule 4511 / SEC Rule 17a-4 record-keeping obligations.
fsi_intake_sponsorbackupgroup M365 group alias, distribution list, or individual UPN for sponsor escalation When the named sponsor does not act within the SLA window, escalation notifications are routed here. Recommended: a team alias, not an individual.

How to set a current value in the maker portal

  • 1

    Open the solution

    Navigate to make.powerapps.com > Solutions > FSI Agent Intake.

  • 2

    Find Environment variables

    In the left filter panel choose Environment variables. You should see all 7 variables listed.

  • 3

    Set the current value

    Click the variable name, then select Edit. Under Current value, enter your environment-specific value. Do not change the Default value field.

  • 4

    Save and repeat

    Save each variable. There is no bulk-save; set each of the 7 individually.

  • 5

    Restart flows

    After setting all 7 values, open each flow that was suspended and turn it On. Power Automate re-reads environment variable values at flow-turn-on time.

Step 5

Classification Zones & Intake Paths

The intake pipeline routes every agent request through up to six binary deny-gate questions (T1–T6). Answers determine whether the request follows the Express, Standard, or Full path and which governance zone applies.

T1–T6 deny gates

Each trigger is a yes/no question; Yes or Not sure both count as a trigger hit and move the request out of Express. Adjust audience-to-zone mappings and quorum thresholds in templates/policy-lookup-tables.yaml if your organization applies different zone boundaries — fsi_acv_zone is the zone option set, not a configuration table.

Applies when an agent can initiate, approve, or trigger a payment, transfer, settlement, or any financial transaction on behalf of a client or the firm.

Regulatory relevance: FINRA Rule 4511 (books and records) and Fed SR 11-7 (model risk). A trigger hit here moves the request out of Express; the final path (Standard or Full) depends on the audience zone and the total number of T1–T6 hits.

Applies when an agent sends responses, recommendations, or disclosures to external clients — retail, institutional, or counterparty.

Regulatory relevance: FINRA Rule 3110 supervision — client-facing communications require designated supervisory review of agent outputs. A trigger hit routes the request to Standard or Full depending on the audience zone and total T1–T6 hits.

Applies when an agent operates in fully automated mode: no human approval step exists between the agent triggering an action and the action completing.

Regulatory relevance: OCC Bulletin 2011-12 and Fed SR 11-7 model-risk-management expectations for autonomous decision models. This trigger raises review depth; when the request lands on the Full path (Tier 1), the MRM handoff runs at the end of board review.

Applies when an agent accesses, stores, or transmits non-public personal information about retail consumers — account numbers, SSNs, income, transaction history, or health data.

Regulatory relevance: GLBA 501(b) — financial institutions must protect NPI. A trigger hit routes to Standard or Full; the Standard board adds the Compliance reviewer to the default InfoSec + Privacy pair when NPI is in scope.

Applies when an agent has access to material non-public information that could influence trading decisions — merger data, undisclosed earnings, regulatory filings before release.

Regulatory relevance: Any positive MNPI answer routes the request directly to the Full path by default, because MNPI handling needs the deepest review (Legal and Compliance sit on the five-role board). This supports FINRA Rule 3110 supervisory review and firm information-barrier controls.

Applies when an agent transfers, replicates, or processes data across geographic or jurisdictional borders — for example, data leaving its declared data-residency country.

Regulatory relevance: CFTC Rule 1.31 (records retention). Cross-border data triggers a default-deny gate when the maker country differs from the declared data-residency country; Privacy can record an override, and an approved cross-border mismatch still routes to the Full path.

Three intake paths

Regulatory alignment

The three-path classification structure is designed to help meet FINRA Rule 3110 (supervision), FINRA Rule 25-07 (AI governance), and SEC Rule 17a-3 (record-keeping). The Full path with board quorum and MRM handoff is required to support OCC 2011-12 and Fed SR 11-7 model risk management obligations for autonomous agents. Zone configuration and classification thresholds must be reviewed by your compliance and legal teams for applicability to your specific regulatory profile.

Step 6

Reviewer Roles & the Queue App

The Full-path reviewer board has five roles — InfoSec, Privacy, Compliance, Legal, and MRM — with a default parallel quorum of 3 of 5. The Standard board is InfoSec + Privacy (default quorum 2 of 3), adding Compliance when the request handles NPI. Each role is a Dataverse security role scoped to the solution.

Assign reviewers to security roles

In Power Platform admin center > Environments > [Your Env] > Settings > Users + permissions > Security roles, assign users or Microsoft Entra groups to the following roles:

Reviewer roleResponsibilitiesRequired for
InfoSec Reviewer Reviews data handling controls, access scope, and security architecture of the proposed agent. Standard path, Full path
Privacy Reviewer Evaluates NPI / PII exposure, consent mechanisms, and data minimization compliance. Standard path, Full path
Compliance Reviewer Assesses alignment with FINRA, SEC, and GLBA requirements applicable to the agent use case. Standard (when NPI is in scope), Full path
Legal Reviewer Reviews contract implications, liability scope, and regulatory filing obligations. Full path
MRM Reviewer Validates model risk classification, documentation package, and handoff to the MRM system. Full path (Tier 1 MRM handoff)

“Governance Lead” is an app security role, not a board reviewer

The five board reviewer roles above (InfoSec, Privacy, Compliance, Legal, MRM) are values in the fsi_intake_reviewerrole option set, alongside Sponsor and Sponsor Manager. Governance Lead is a separate concept — a security role defined in the reviewer model-driven app (reviewer-app-spec.json) for app access, not a member of the quorum board. Full-path approval is reached by the 3-of-5 board quorum, not by a single chair.

Group vs. individual assignment

Assigning Entra groups (rather than individuals) to security roles allows role membership to be managed through normal Entra group-membership processes without touching Power Platform on every personnel change. Recommended for all reviewer roles.

Using the model-driven reviewer queue app

  • 1

    Open the app

    Navigate to the URL stored in fsi_intake_reviewerappurl. Reviewers can also bookmark it directly or access it from the Teams adaptive card link.

  • 2

    Review the queue view

    The default view shows pending intake requests assigned to your reviewer role. Active views: Pending Review, Awaiting Sponsor, Board Quorum, Approved, Denied, All Active.

  • 3

    Open a record

    Click a request to open the fsi_intakerequest form. The form shows the maker submission, T1–T6 classification answers, data source declarations, risk signals, and the full decision log.

  • 4

    Enter your decision

    Select Approve, Deny, or Request More Information. Your decision, timestamp, and role are written to fsi_intakedecisionlog automatically.

  • 5

    Monitor the audit trail

    The fsi_intakedecisionlog table records every reviewer action with fsi_requestid, reviewer UPN, decision, timestamp, and notes. This log is the primary audit artifact for examination readiness.

FINRA Rule 3110 — Supervision

Assigning named supervisors to reviewer roles and recording their decisions in fsi_intakedecisionlog helps meet the written supervisory procedure requirements of FINRA Rule 3110. The log should be retained per the FSI-AgentIntake-7yr retention label; see Step 8.

Step 7

Retention Label & Microsoft Entra Agent ID

Two post-deploy tasks complete the governance posture: applying the 7-year retention label and minting a Microsoft Entra Agent ID for each approved agent (Express, Standard, and Full).

7a — Purview retention label: FSI-AgentIntake-7yr

If you did not pass -SkipPurviewLabel, the deploy script attempts to create and publish this label automatically via ExchangeOnlineManagement. To create it manually:

  1. Open Microsoft Purview compliance portal > Data lifecycle management > Retention labels.
  2. Select + Create a label. Name it exactly FSI-AgentIntake-7yr.
  3. Set the retention period to 7 years (2555 days), counted from when the item was created (CreationAgeInDays).
  4. Set the action after the retention period to Retain and take no action — this matches the deploy script's RetentionAction Keep. Do not configure auto-delete or disposition review.
  5. Create a second, immutable label named FSI-AgentIntake-7yr-WORM with the same 7-year duration and Mark items as records enabled. The immutable decision log (fsi_intakedecisionlog) is stamped with this WORM label.
  6. Publish both labels to the relevant SharePoint locations and Dataverse environments.
  7. Copy the label GUID from the label detail page and paste it into the fsi_intake_retentionlabelid environment variable.

FINRA Rule 4511 + SEC Rule 17a-4 — Record retention

FINRA Rule 4511 requires broker-dealers to retain required books and records for at least 6 years. SEC Rule 17a-4 additionally requires that records be stored in a non-rewriteable, non-erasable format (WORM) for at least 3 years (first 2 years in an accessible location). The FSI-AgentIntake-7yr label is designed to support this obligation. Consult your Compliance and Legal teams to confirm the label parameters meet your firm-specific requirements before publishing.

7b — Microsoft Entra Agent ID setup

On approval, the pipeline mints a Microsoft Entra Agent Identity for the new agent — on every path (Express, Standard, and Full). This step requires admin consent for Graph application permissions.

Pre-requisites:

  • Entra Global Administrator or Privileged Role Administrator must grant admin consent for the Graph application permissions: AgentIdentity.CreateAsManager or AgentIdentity.Create.All.
  • Grant consent in Microsoft Entra admin center > App registrations > [your app] > API permissions > Grant admin consent.

Generate the Agent Identity blueprint:

# Run from the solution root directory
python scripts/setup_agent_identity_blueprint.py --output .\agent-identity-blueprint.json

The script returns an agentIdentityBlueprintId. Store this value — it is referenced by the approval flow when it calls the Microsoft Graph custom connector to mint the Agent ID.

How minting works in the intake pipeline:

  1. When a request is approved — sponsor 1-click for Express, or board quorum for Standard and Full — the approval flow calls the fsi_cr_graph_agentintake connection reference.
  2. The Graph custom connector posts a create-agent-identity request using the blueprint ID and the intake request data from fsi_intakerequest.
  3. The returned Entra Agent ID (object ID) is written back to the fsi_intakerequest record and recorded in fsi_intakedecisionlog.
  4. The maker receives a Teams notification with the Agent ID, enabling them to reference it in downstream governance checks (drift detector, scope monitor).

Admin consent is a one-time step per tenant

Once a Global or Privileged Role Administrator grants consent for AgentIdentity.CreateAsManager, all subsequent approvals in that tenant can mint Agent IDs without additional admin intervention. Verify consent is in place before processing your first approval.

Step 8

Operate the Pipeline

Day-to-day operation centers on three activities: monitoring flow health, reading the decision-log audit trail, and managing handoffs to downstream governance systems.

Power Automate run history: Open Power Apps > Solutions > FSI Agent Intake, select Cloud flows, and review run history for each flow. Failed runs show with a red icon; drill into any failure to view the error and affected action.

Common suspend reasons:

  • Unbound connection reference — flow suspends immediately on first trigger. Fix: bind the reference (Step 3), then turn the flow Off and On to restart it.
  • Environment variable not set — flow reads a null value and fails on the first HTTP or Teams action. Fix: set the missing variable (Step 4), then restart the flow.
  • Alt-key latency — a flow that filters by fsi_requestid using the alternate-key URI form may receive HTTP 400 within 30–90 seconds of table creation. The resilient pattern filters using fsi_requestid eq '...' and retrieves the primary key before constructing the URI.

Smoke test re-run: After fixing a configuration issue, run pwsh scripts/smoke_test.ps1 to validate end-to-end path execution across all three intake paths.

Structure: fsi_intakedecisionlog is the immutable decision-pack record — one row per intake decision (per-reviewer votes live in fsi_intakeapproval / fsi_intakereview). Each row contains:

  • fsi_requestid — links to the parent fsi_intakerequest record.
  • fsi_decisionoutcome — Approved (100000000), AutoApproved (100000001), Denied (100000002), EscalatedToManager (100000003), or WithdrawnByMaker (100000004).
  • fsi_risktier, fsi_zone, and fsi_pathused captured at decision time.
  • fsi_decidedon (UTC), fsi_policyversionapplied, and the tamper-evident fsi_decisionpackjson + fsi_decisionpackhash (SHA-256).
  • fsi_retentionlabelapplied and fsi_retentionlabelappliedon — the stamped Purview label and timestamp.

Querying via OData:

GET https://<org>.crm.dynamics.com/api/data/v9.2/fsi_intakedecisionlogs
?$select=fsi_requestid,fsi_decisionoutcome,fsi_risktier,fsi_pathused,fsi_decidedon
&$filter=fsi_decisionoutcome eq 100000000
&$orderby=fsi_decidedon desc
&$top=50

Export for examination: Use Power Automate or the Dataverse OData API to export fsi_intakedecisionlog rows for a given date range. The export should be retained per the FSI-AgentIntake-7yr label.

MRM handoff (Full path): When a Full-path (Tier 1) agent is approved and MRM review is required, the flow posts the intake decision pack payload to the URL in fsi_intake_mrmtargetenv. Verify the target URL is reachable and that the HTTP with Entra ID connector is properly scoped to authenticate against it.

Drift-detector handoff (Standard + Full): At close of review, the flow posts an initial scope snapshot to fsi_intake_driftdetectorenv. This seeds the drift-detector baseline for the new agent. Confirm the drift detector is running in the target environment before enabling this path.

Decision packs: The fsi_intakedecisionlog rows associated with a request collectively form the “decision pack” — the full chronological record of reviewer actions, timestamps, and outcomes. The decision pack is referenced during examination responses and post-incident reviews. Maintain at least one export procedure for on-demand production of decision packs per intake request.

Monitoring checklist (recommended weekly)

  • ✓

    Review suspended flows

    Open Solutions > FSI Agent Intake > Cloud flows. Any flow showing Suspended requires immediate attention — it is not processing intake requests.

  • ✓

    Check overdue queues

    In the reviewer queue app, check the Awaiting Sponsor and Board Quorum views for requests that have been open longer than your SLA. Trigger escalation via the fsi_intake_sponsorbackupgroup channel if needed.

  • ✓

    Verify MRM + drift handoffs

    Search fsi_intakedecisionlog for Full-path approvals in the past week and confirm corresponding entries in your MRM system and drift-detector baseline table.

  • ✓

    Confirm retention-label application

    Spot-check fsi_intakeretentionrecord rows to confirm the FSI-AgentIntake-7yr label is being applied to new decision records.

Step 9

Troubleshoot & Key Takeaways

Common configuration traps and their resolution steps. If a problem persists after following these steps, enable -DryRun and review the structured log output for the failing stage.

Common traps

  • !

    Connection reference not found in FSIAgentIntake solution

    Symptom: Flow fails on first trigger with “Connection reference was not found.” The reference exists in the environment but is in the Default solution.
    Cause: The connection reference was created outside the solution context, or the deploy script ran before the solution container was created.
    Fix: Add the reference to the solution: pac solution add-solution-component --solutionUniqueName FSIAgentIntake --component <id> --componentType connectionreference (use the name, not a numeric code).

  • !

    pac componentType numeric code rejected

    Symptom: pac solution add-solution-component returns “not known, Please provide the Component Type name.”
    Cause: You passed a numeric code such as 371 or 10137.
    Fix: Replace the numeric code with the string connectionreference. The pac CLI resolves component types by name only for this component type.

  • !

    Flow suspended immediately after turning On

    Symptom: A flow shows Suspended within seconds of being turned on.
    Cause: Usually an unset environment variable or an unbound connection reference.
    Fix: Check all 7 env vars are populated (Step 4) and every connection reference is bound (Step 3) — the four standard references, plus the optional Graph reference if the custom connector was provided. Turn the flow Off, then On after each fix.

  • !

    Alt-key HTTP 400 on fsi_requestid lookup

    Symptom: A flow using the alternate-key URI form for fsi_intakerequest receives HTTP 400 immediately after the table was created.
    Cause: Dataverse takes 30–90 seconds to build the index for the fsi_RequestIdUniqueKey alternate key on fsi_requestid. The index is not available immediately.
    Fix: Use a filter query ($filter=fsi_requestid eq '<value>') to retrieve the primary GUID, then construct the primary-key URI. This approach is resilient regardless of index state.

  • !

    Duplicate connection reference created

    Symptom: Binding appears to succeed, but flows still fail because they reference a different logical name.
    Cause: Clicking “+ New connection reference” in the designer generated a new reference with a different logical name (e.g., fsi_dataverseagentintake instead of fsi_cr_dataverse_agentintake).
    Fix: Delete the duplicate reference and bind the original. Confirm the reference logical names in Solutions > FSI Agent Intake > Connection references match exactly those listed in Step 3.

  • !

    Purview label not published after deploy

    Symptom: fsi_intake_retentionlabelid is empty; fsi_intakeretentionrecord rows are created but not labeled.
    Cause: The -SkipPurviewLabel switch was used and the label was not created manually, or the label was created but not published to the Dataverse environment.
    Fix: Create and publish FSI-AgentIntake-7yr in Purview (Step 7a), then set the GUID in fsi_intake_retentionlabelid.

  • !

    MRM handoff fails silently

    Symptom: Full-path approval completes but no record appears in the MRM system.
    Cause: The URL in fsi_intake_mrmtargetenv is unreachable from the Power Automate service, or the HTTP with Entra ID connection is not authorized for the MRM endpoint.
    Fix: Test the MRM endpoint URL with a manual HTTP call using the same service account. Verify the Entra app registration has the required permissions on the MRM API. Check the flow run history for the failing HTTP action.

Key Takeaways

  • Bind existing references, never create new ones. Connection references must be components of FSIAgentIntake with the exact logical names listed in Step 3. Creating new ones generates different names that flows will not find.
  • Use --componentType connectionreference (the string, not a number). The pac CLI requires the type name; numeric codes are rejected for this component type.
  • Set current values for all 7 environment variables before turning flows on. Missing values suspend flows immediately. Always set current values — do not edit the default values.
  • T1–T6 gate answers drive path and zone. Zero trigger hits and a Zone-3 audience yield Express / Tier 3 / Zone 3; any hit (Yes or Not sure) routes to Standard or Full by audience zone and hit count. Adjust thresholds in templates/policy-lookup-tables.yaml — fsi_acv_zone is the zone option set, not a table.
  • fsi_intakedecisionlog is the primary audit artifact. Every reviewer action, timestamp, and role is recorded here. Export this table per your examination-response procedures and retain it under the FSI-AgentIntake-7yr label.
  • Admin consent for Entra Agent ID is a one-time tenant-level step. Grant consent for AgentIdentity.CreateAsManager or AgentIdentity.Create.All before the first approval completes — Agent IDs are minted on every path.
  • Run smoke tests after every configuration change. pwsh scripts/smoke_test.ps1 validates all three intake paths (Express, Standard, Full) end-to-end, including the denial scenarios.
