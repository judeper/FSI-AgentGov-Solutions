Extending agent-intake: schema, flows, and the contracts that hold them together

A self-guided tour for developers and DevOps engineers who will extend the agent-intake governance gate. You will learn how the solution is built — its soft-FK evidence schema, its twelve Power Automate flows, the classifier engine, and the hand-build mechanics — so you can add reviewer roles, classification rules, and handoff targets without breaking the immutable records that support FINRA Rule 4511 and SEC Rule 17a-4.

⏱ ~18 min read No environment needed v1.0.0-preview

v1.0.0-preview — pilot-validation content: suitable for pilot validation and extension work, not broad production rollout without the firm's own governance sign-off.

What you'll learn

  • Trace a request through the 12 flows and name the contract each one preserves.

ARCHITECTURE · THE EVIDENCE SCHEMA

Nine tables, one soft foreign key

Agent-intake stores its decision pack across nine Dataverse tables. One is the parent request; the other eight are evidence. The design choice that makes the evidence defensible is a soft foreign key: every child table carries the request identifier as a string column — fsi_requestid — not a Dataverse lookup relationship.

Why a string, not a lookup?

A Dataverse lookup enforces referential integrity: delete the parent and the platform cascades or blocks. That is exactly the wrong behavior for books-and-records evidence. Agent-intake instead writes the parent's fsi_requestid GUID into a plain text column on each child. The link is resolved at query time ($filter=fsi_requestid eq '<id>'), so an immutable fsi_intakedecisionlog record survives parent deletion — the evidence does not vanish when a maker withdraws or a request row is later cleaned up.

Why this design supports the records rules

The immutable fsi_intakedecisionlog (OrganizationOwned, 7-year retention label FSI-AgentIntake-7yr) supports compliance with FINRA Rule 4511 and SEC Rule 17a-4 (books & records / retention) and CFTC Rule 1.31. The soft-FK keeps that record readable after the operational parent is gone. Implementation requires organizations to verify the retention label and access model against their own obligations.

Read the schema as three layers

Holds the maker inputs (agent details, sponsor, the fsi_t1initiatesfinancialtxn … fsi_t6crossborderdata trigger answers) and the router's outputs: fsi_pathused, fsi_risktier, fsi_zone, fsi_decisionpath, fsi_quorumrequired, fsi_parallelreviewersjson, fsi_mrmrequired, fsi_mrmhandoffstatus, and fsi_status. An alternate key fsi_RequestIdUniqueKey covers fsi_requestid.

fsi_intakedatasource (declared connectors, 1..N), fsi_intakerisksignal (one row per trigger answer), fsi_intakereview (reviewer outcomes in fsi_reviewoutcome, not a column named fsi_reviewdecision), fsi_intakeapproval (per-approver decisions), and fsi_intakesponsorship (the sponsor attestation surface). Each carries fsi_requestid as a string.

fsi_intakedecisionlog stores the full decision pack in fsi_decisionpackjson plus a SHA-256 in fsi_decisionpackhash; fsi_intakeauditevent is the lifecycle trail (fsi_eventtype is a string, so customers can extend the event vocabulary without a schema change); fsi_intakeretentionrecord records each retention-label stamp. All three are OrganizationOwned so they are not tied to a single user's records.

A new alternate key takes 30–90 seconds to build its index, during which the alt-key URI form fsi_intakerequests(fsi_requestid='…') returns HTTP 400. The resilient pattern used in the seed and smoke scripts is: filter by fsi_requestid eq '…', read the GUID fsi_intakerequestid from the result, then operate via the primary-key URI. Keep this pattern when you extend the scripts — do not revert to the alt-key URI form.

ORCHESTRATION · 12 FLOWS

How a request moves through twelve flows

Twelve documented Power Automate cloud flows carry a request from submission to live tracking. The macro lifecycle has five beats; the flows below implement them. By repo policy the flows are documented for manual build — there is no exported flow JSON.

The twelve flows, grouped

Each card names the flow, its trigger, and the contract it preserves. The numeric choice values (for example fsi_status = Submitted (100000001)) are the real option-set integers used in trigger conditions.

fsi-intake-router triggers on fsi_intakerequest where fsi_status = Submitted (100000001), calls the classifier contract, re-checks the sponsor self-approval gate, writes fsi_pathused, fsi_decisionpath, fsi_risktier, fsi_zone, fsi_quorumrequired, fsi_parallelreviewersjson, then sets fsi_status = InReview (100000011) or Denied (100000005). fsi-intake-presubmit-classifier is the stateless HTTP endpoint that returns the same shape the Power Pages form consumes — it writes nothing.

fsi-intake-sponsor-card triggers where fsi_pathused = Express (100000000) and fsi_status = InReview. It posts templates/sponsor-approval-card.json with the FINRA Rule 3110 attestation language, writes an fsi_intakeapproval row and an fsi_intakesponsorship row, then on approval calls Flow 8 and sets fsi_status = Approved (100000004). Express keeps a single sponsor approval as its only reviewer evidence.

fsi-intake-parallel-reviewers fans out one fsi_intakereview row per reviewer parsed from fsi_parallelreviewersjson. fsi-intake-reviewer-decision-handler processes each Teams response, recomputes weighted quorum against fsi_quorumrequired (any Denied ends the request, no override), and sets fsi_nonmrmquorummet. fsi-intake-escalation is a daily recurrence that chases overdue Pending (100000000) reviews past fsi_dueon.

fsi-intake-mrm-handoff triggers where fsi_pathused = Full (100000002), fsi_mrmrequired = true, fsi_nonmrmquorummet = true, and fsi_mrmhandoffstatus is Pending (100000000) or Failed (100000003). It composes the templates/mrm-handoff-payload-schema.json payload, upserts model-risk-management-automation, and sets fsi_mrmhandoffstatus = Handed off (100000001). This step supports compliance with OCC 2011-12 and Federal Reserve SR 11-7.

fsi-intake-decision-pack-writer is a child flow invoked by Flows 3, 5, and 7. It reads the request plus all evidence rows, composes the decision-pack JSON in the drift-envelope shape, computes the SHA-256 hash, and inserts the immutable fsi_intakedecisionlog row. Idempotency is a flow step, not a database constraint: before inserting, it queries fsi_intakedecisionlog for the same fsi_requestid + fsi_decisionpackhash and skips the insert when a match already exists. Because every other approval path depends on it, this is the flow you build and turn on first (see Flow-build mechanics).

fsi-intake-registry-handoff fires on fsi_status = Approved, mints the Microsoft Entra Agent ID into fsi_entraagentid, hands the decision-pack envelope to agent-registry-automation (writing fsi_registryrecordid), and sets fsi_status = LiveTracking (100000012). fsi-intake-drift-handoff then posts the templates/drift-handoff-payload-schema.json payload to the detector configured in fsi_intake_driftdetectorenv.

fsi-intake-denial-appeal listens for the denial-card denialAppeal action, checks the per-path appeal cap, and creates a fresh fsi_intakerequest with fsi_appealofid preserving lineage (Flow 1 re-picks it up once it reaches Submitted). fsi-intake-retention-tagger stamps the retention label and writes fsi_intakeretentionrecord evidence for new decision-log, audit, and final-state rows — it is a logical pattern, since one cloud flow cannot trigger on multiple Dataverse tables.

CLASSIFIER ENGINE

How a request becomes Express, Standard, or Full

The classifier in seed_classification_rules.py reads the maker's six trigger answers and the agent's audience/zone, then derives a path, a risk tier, a governance zone, the reviewer roster, and the quorum. Flow 1 (router) calls the same logic at runtime; the HTTP classifier (Flow 2) mirrors it for the pre-submit preview.

The three-step derivation

  1. 1

    Count the trigger hits

    Each of fsi_t1initiatesfinancialtxn through fsi_t6crossborderdata is a three-state answer. Yes and Not sure both count as a positive hit; only an explicit No is zero. T5 marks material non-public information (MNPI); T6 marks cross-border personal data.

  2. 2

    Derive the provisional path

    Express needs zero hits and a Zone 3 audience → Tier 3, sponsor-only, quorum 1. Standard is 1–2 non-MNPI hits or a Zone 2 audience → Tier 2, InfoSec + Privacy (+ Compliance when a T4 NPI hit is present), 2-of-3 quorum. Full is three or more hits, any T5 MNPI hit, a Zone 1 audience, or a Privacy-approved cross-border case → Tier 1, InfoSec + Privacy + Compliance + Legal + MRM, 3-of-5 quorum. The path is the highest any single rule reaches.

  3. 3

    Apply the deny gates

    Two gates can override the derived path with an immediate Denied (100000005) outcome before any reviewer is engaged — see the warning below. Otherwise the router writes the path, tier, zone, roster, and quorum onto the parent request and moves it to InReview (100000011).

Two deny gates short-circuit the path

Sponsor self-approval (ADR-008): when fsi_sponsorupn equals fsi_makerupn, the request is denied — a maker cannot sponsor their own agent. Cross-border default-deny (ADR-005): a T6 hit where the maker's country differs from the data-residency region and no fsi_privacyoverride is set denies by default. Both gates re-run inside Flow 1, not just in the pre-submit preview, so a client that skips the preview is still gated.

Regulation reference

The MNPI (T5) and cross-border personal-data (T6) triggers route handling that supports compliance with GLBA 501(b) safeguards for non-public personal information. Tier 1 / Full requests add a model-risk review that helps meet OCC 2011-12 and Federal Reserve SR 11-7 expectations. The thresholds are policy inputs you tune in policy-lookup-tables.yaml, not guarantees of a regulatory outcome.

FLOW-BUILD MECHANICS

The Power Automate consensus that keeps flows from failing silently

These six patterns come from the three-report build research recorded in AGENTS.md. Most failures here are silent — the flow reports success while writing nothing — so treat each card as a checklist item when you add or modify a flow.

A callable child flow (Flow 8) must use the "Manually trigger a flow" trigger with Text inputs that you json()-parse inside. It must hit a "Respond to a Power App or flow" action on every branch — if any path can finish without responding, the parent waits roughly 30 days. The child must also live in the same FSIAgentIntake solution and be saved, published, and turned ON, or the "Run a Child Flow" picker silently omits it.

The canonical contract is the Dataverse trigger "When a row is added, modified or deleted" with Change type = Added and Modified, Table = Intake Requests, and Scope = Organization, guarded twice so a replay or the router's own write-back cannot re-route the row: a Filter rows OData expression on fsi_status eq 100000001 (Submitted) plus a blank or stale fsi_decisionpath, and a Trigger condition @equals(triggerOutputs()?['body/fsi_status'], 100000001) — note the bare leading @, which Power Automate requires on trigger conditions only. Once the router stamps fsi_decisionpath and flips fsi_status to InReview, the Modified re-fire no longer passes the guard. Change type = Added only is a lab/slice optimization on top of this contract — valid because New-IntakeSubmission.ps1 writes a fresh Submitted row per run, so an Added-only trigger fires on creation and sidesteps self-retrigger without leaning on the guards. Treat it as a lab shortcut, not the universal rule.

When an Update or Add row action sets a choice column, supply the option-set integer (for example fsi_status = 100000004 for Approved), never the display label "Approved". A label posts a NULL for that column and Dataverse still returns HTTP 204, so the step looks green while the value never lands. Every status, path, tier, and zone value in this solution is an integer in the 100000000+ range — keep a copy of the choice-value table from flow-configuration.md open while you build.

The soft-FK means you resolve a request through List rows with a fsi_requestid eq '…' filter, then read the single match with first(outputs('List_rows')?['body/value']). Always branch on empty(outputs('List_rows')?['body/value']) first — calling first() on an empty collection fails the run. This is the same resilient pattern the seed and smoke scripts use instead of the alternate-key URI.

There is no expression to compute SHA-256 inside a cloud flow. Flow 8 writes a deferred marker — concat('sha256-pending:', guid()) — into fsi_decisionpackhash, and a downstream job (an Azure Function or the registry handoff) computes the real digest over the canonical fsi_decisionpackjson bytes and updates the row. Keep the marker prefix stable so consumers can tell a pending hash from a final one.

Build the shared child (Flow 8) first so the callers can bind to it, and wire the router (Flow 1) last so nothing fires before its dependencies are ON. Validate with the three adversarial checks from the research: a loop test (confirm the router does not re-fire on its own writes), a child-null-return test (confirm a child that responds with no payload does not wedge the parent), and a connection-identity test (confirm the flow runs as the intended service identity, not the maker).

The failure mode here is silence

A mislabeled choice value, a child flow left in the Default solution, or a missing Respond branch all produce a run that reports success while doing nothing. Verify writes by reading the row back — the Get-IntakeFlowState.ps1 harness exists for exactly this reason.

EXTENSION POINTS

Five ways to extend without breaking the evidence chain

Each extension point has a supported seam. The rule that ties them together: the immutable evidence tables and the handoff payloads are contracts. You can add to them, but renaming or removing a top-level key breaks downstream consumers.

Add the new role as an option in the fsi_intake_reviewerrole option set (next integer in the 100000000+ sequence), map it to the paths and quorum weights in policy-lookup-tables.yaml, and the classifier will emit it inside fsi_parallelreviewersjson. Flow 4 fans out one fsi_intakereview row per entry, so no flow edit is needed — the roster is data-driven. Re-run the classifier self-test to confirm the new role appears in the expected paths.

Thresholds, zone mappings, and quorum sizes live in policy-lookup-tables.yaml and the rule logic in seed_classification_rules.py. Per ADR-009 a change that moves a request's tier (T1–T6 weighting, a new trigger, a quorum size) is a major modification: bump the policy version so existing decision packs stay pinned to the rules in force when they were approved, and add a pytest case alongside the existing 42 so the new branch is covered. Avoid editing tier outcomes inline in a flow — keep the logic in the classifier.

To hand the approved agent to another downstream solution, add a flow that triggers on fsi_status = LiveTracking (100000012) and composes a payload that extends the existing drift envelope rather than redefining it. Keep all 18 required top-level keys (from drift-handoff-payload-schema.json) so existing consumers keep parsing; add your fields under a nested object. Carry requestId and decisionPackHash as the correlation keys.

The solution ships five connection references — fsi_cr_dataverse_agentintake, fsi_cr_teams_agentintake, fsi_cr_office365_agentintake, fsi_cr_http_agentintake, and fsi_cr_graph_agentintake. When you add another, register it with the solution by its name (--componentType connectionreference), not the numeric component type — otherwise it lands in the Default solution and never appears under FSIAgentIntake. Then gate deployment with Test-IntakeConnectionBinding.ps1.

The decision pack stored in fsi_decisionpackjson is the canonical evidence object, and its SHA-256 in fsi_decisionpackhash is computed over its bytes — so any change to the serialization changes the hash. Add new evidence under a nested object and keep the existing top-level keys and their ordering stable. The fsi_eventtype string column on fsi_intakeauditevent is the deliberate no-schema-change seam for new lifecycle event names. Update the decision-pack-writer (Flow 8) and re-run the smoke test after any envelope change.

Regulation reference

Versioning classification rules and pinning each decision pack to the policy version in force supports compliance with the record-keeping expectations of FINRA Rule 4511 and SEC Rule 17a-4. It remains the deploying organization's responsibility to verify the configuration against its own supervisory obligations.

AUTOMATION HARNESS

The four scripts that provision, seed, and validate

A repeatable loop wraps the manual flow build: provision the solution shell, gate on bound connections, drop a test submission, then activate the flows child-first. Run them in this order on a fresh environment.

  1. 1

    Provision the solution shell

    provision_solution_shell.ps1 creates the FSIAgentIntake unmanaged solution, its environment variables, and the five connection references — idempotently, so re-runs are safe. Watch its output for MANUAL STEP REQUIRED: lines, which flag the designer actions a script cannot perform.

    pwsh ./scripts/provision_solution_shell.ps1 -EnvironmentUrl <org-url>
  2. 2

    Gate on bound connections

    Test-IntakeConnectionBinding.ps1 verifies each connection reference resolves to a live connection before you build flows on top of it. Pass -RequireBound to fail the run unless the named references are bound — use it as a deployment gate in CI.

    pwsh ./scripts/Test-IntakeConnectionBinding.ps1 -EnvironmentUrl <org-url> `
  -RequireBound fsi_cr_dataverse_agentintake,fsi_cr_teams_agentintake
  3. 3

    Drop a test submission

    New-IntakeSubmission.ps1 writes a pristine Submitted request to trigger the router. Pick a -Scenario to exercise a path (for example express-happy, full-parallel-board, cross-border-deny, or sponsor-self-approval-deny). Add -PreClassify to stamp the router outputs so you can test a single downstream flow as a vertical slice without standing up Flow 1 first.

    pwsh ./scripts/New-IntakeSubmission.ps1 -EnvironmentUrl <org-url> `
  -Scenario full-parallel-board -PreClassify
  4. 4

    Activate the flows child-first

    Get-IntakeFlowState.ps1 reports each flow's on/off state and, with -Activate, turns them on in a safe order. Pass -ActivationOrder with the child flow first so the parents never bind to a child that is not yet published — this avoids the ChildFlowNeverPublished race. Use -ExpectedCount to assert the full set is present.

    pwsh ./scripts/Get-IntakeFlowState.ps1 -EnvironmentUrl <org-url> `
  -Activate -ActivationOrder fsi-intake-decision-pack-writer -ExpectedCount 12

Two ordering rules the harness encodes

Register connection references by name so they land in the FSIAgentIntake solution, and activate the shared child (Flow 8) before its callers so the "Run a Child Flow" binding resolves. The scripts encode both — keep that order if you extend them.

CONTRACTS & TESTING

What you must not break — and how to prove you didn't

Three things are load-bearing for downstream consumers: the handoff payload shapes, the decision-pack hash, and the correlation keys that stitch flows together. Treat their top-level structure as a published contract.

9Dataverse tables in the evidence model
12Documented Power Automate flows
18Required keys in the drift payload
13Required keys in the MRM payload

Contracts to preserve

drift-handoff-payload-schema.json requires 18 top-level keys — payloadVersion, originIntakeId, pathUsed, riskTier, zone, declaredDataSources, connectorAllowlist, reviewerAttestations, mrmHandoffStatus, decisionPackHash, entraAgentId, and others. mrm-handoff-payload-schema.json requires 13, including $schema, intake, agent, model, controls, reviewers, and decisionPackHash. Add fields under nested objects; do not rename or drop a top-level key.

fsi_decisionpackhash is a SHA-256 digest of the canonical fsi_decisionpackjson bytes. Both handoff payloads echo it as decisionPackHash, so a consumer can confirm it received the same evidence the intake recorded. Any change to how the pack is serialized changes the hash — which is the point. Keep the serialization deterministic and keep the sha256-pending: marker prefix for the brief window before the digest is finalized.

fsi_requestid (surfaced as requestId / originIntakeId) is the spine that links every evidence row and every handoff back to one intake. Reviewer rows additionally carry their review identifier and fsi_reviewerrole, and the decisionPackHash ties the immutable decision log to the payloads. Preserve these when you add a flow so a request stays traceable end to end.

Prove it before you ship

Three commands cover the unit, classifier, and deployment layers. Run all three after any schema, classifier, or flow change:

# 1. Unit + integration suite (schema, identity, retention, classifier)
python -m pytest agent-intake/tests

# 2. Classifier self-test — re-derive every path from the rule fixtures
python agent-intake/scripts/seed_classification_rules.py --self-test

# 3. Deployment smoke test against a live environment
pwsh agent-intake/scripts/smoke_test.ps1 -EnvironmentUrl <org-url>

A renamed key is a silent break

Downstream solutions parse these payloads by key name. Renaming or removing a top-level key compiles and deploys cleanly but breaks the consumer at runtime. When in doubt, add under a nested object and bump payloadVersion rather than reshaping the envelope.

RECAP

Key takeaways

If you remember five things from this module, make it these. Each maps to an objective from the top of the page.

What to remember

  • The evidence model is nine tables joined by a string soft-FK (fsi_requestid), not lookups — so the OrganizationOwned fsi_intakedecisionlog, fsi_intakeauditevent, and fsi_intakeretentionrecord rows outlive their parent, which supports compliance with FINRA 4511 / SEC 17a-4.
  • Twelve flows implement one lifecycle. Build the shared child fsi-intake-decision-pack-writer first and the router last, and let the data-driven roster in fsi_parallelreviewersjson do the fan-out.
  • The classifier derives Express / Standard / Full from six trigger hits and the zone, where Yes and Not sure both count; two deny gates (sponsor self-approval, cross-border) can override the path before any reviewer is engaged.
  • Most flow-build failures are silent: write choice columns as integers, give a callable child a Respond on every path inside the same solution, trigger the router on Added + Modified behind the Submitted and stale-path guards, and guard first() with empty(). Verify writes by reading the row back.
  • Extend by adding, never by renaming: keep the 18 drift and 13 MRM top-level payload keys and the decisionPackHash stable, register connection references by name, and prove every change with pytest, the classifier self-test, and the smoke test.
