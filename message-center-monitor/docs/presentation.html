The problem

Microsoft posts platform changes to the M365 Message Center every day. Some change how Copilot Studio agents behave. In a regulated environment, "we read the e-mail digest" is not enough.

Regulatory pressure

  • FINRA Rule 3110 — supervisory system must address technology changes affecting client communications.
  • FINRA Rule 4511 — books-and-records retention for the assessment trail.
  • SOX 302/404 — controls over change-management for systems supporting financial reporting.
  • OCC 2011-12 / SR 11-7 — model risk management for AI/ML-driven decisions.

Operational reality

  • Message Center e-mail digest goes to a shared mailbox; gets ignored.
  • No audit trail for "did anyone assess MCxxxxxx?"
  • When an admin does assess a post, their notes live in a Wiki / e-mail / Teams thread — disconnected from the platform record.
  • Re-syncing the post wipes out the admin's work (the C1 regression class).

The solution at a glance

A Dataverse-backed, supervised assessment workflow with three guarantees engineers care about.

1. Daily sync

A scheduled PowerShell job pulls Message Center posts from Microsoft Graph and upserts them into a custom Dataverse table — idempotent, retry-aware, managed-identity-first.

2. Admin assessment workflow

Each row exposes 7 admin-owned columns (status, notes, who, when, actions, agent-impact flag, notify date). Power Apps form, model-driven view, or Power Automate — pick your front end.

3. Sync never overwrites the admin

The "C1 invariant": once an admin sets any of those 7 columns, no future Graph sync may touch them. Enforced by code — and verified end-to-end by the lab dry-run.

Bonus (v2.5.0): a numbered lab/ harness (00→06, 99) bootstraps a complete non-prod deployment in < 30 minutes and runs an end-to-end smoke test that proves the C1 invariant against live Power Platform wires.

Architecture

Daily poll → managed-identity auth → idempotent upsert → admin assessment → Teams alert (severity-gated).

The Dataverse table — two ownership zones

Every column on fsi_messagecenterlog belongs to exactly one of two owners. The C1 invariant is: sync only ever writes to Graph-owned columns.

21 total columns (13 Graph + 7 admin + 1 system primary). The 7 admin-owned columns are the audit trail FINRA / SOX cares about.

End-to-end flow (re-sync, the C1 path)

First PATCH attempts CREATE; on 412 the row exists, so a second PATCH without If-None-Match and without admin columns merges only Graph-owned fields. Idempotent and admin-safe.

C1 — what the v2.4.0 fix actually changed

In v2.3.0 the inline upsert sent fsi_assessmentstatus on every PATCH — silently resetting any value the admin had just set. v2.4.0 routes the update through a helper that excludes ALL 7 admin columns from the update payload.

Before (v2.3.0)

# 09:00 — admin assessed MC54321
fsi_assessmentstatus = Reviewed
fsi_assessment       = "No agent impact, FYI only"
fsi_assessedby       = jane@contoso.com
fsi_assesseddate     = 09:00 UTC
fsi_actionstaken     = "Filed in change log"

# 09:15 — sync runs again
PATCH fsi_messagecenterlogs(fsi_messagecenterid='MC54321')
  fsi_assessmentstatus = NotAssessed   ← clobbered
  fsi_title            = "..."
  fsi_body             = "..."

# Result: admin's work GONE.

After (v2.4.0)

# 09:00 — admin assessed MC54321 (same as before)

# 09:15 — sync runs again
PATCH fsi_messagecenterlogs(fsi_messagecenterid='MC54321')
  If-None-Match: *
  body = { fsi_title, fsi_body, ..., fsi_assessmentstatus=NotAssessed }
  → 412 Precondition Failed

PATCH same URL (no If-None-Match)
  body = { fsi_title, fsi_body, ... }   ← NO admin columns
  → 204 No Content

# Result: admin's 7 columns untouched. ✓
Verified by: 8 mock unit tests in tests/Upsert.Tests.ps1 (set-intersection assertions on the JSON body) + lab Step 6 against live Dataverse (back-dates fsi_lastupdated to force the update path, then asserts byte-equality of all 7 admin columns).

Authentication — managed-identity-first

All three governance scripts accept -AuthMode. Pick the highest-trust mode the host supports.

ModeWhen to useSecrets on disk?Recommended for
ManagedIdentityAzure-hosted runner (Functions, Automation, ACI, AKS, App Service)NoneProduction (default)
WorkloadIdentityGitHub Actions OIDC, Azure DevOps OIDC, federated SPNoneCI / pipelines
InteractiveAdmin workstation, one-off runNoneAd-hoc admin
DeviceCodeHeadless workstation, no browserNoneAd-hoc admin
ClientSecretPower Automate cloud flow, legacy environmentsYes — Key Vault requiredLab / legacy only
Why managed identity matters here: Message Center sync runs every day, unattended. ClientSecret leaves a 24-month-rotating credential in Key Vault that must be audited, rotated, and explained to FSI Security. Managed identity has none of those obligations.

Day-to-day use — the assessment workflow

Step 1 — Triage

Open the model-driven app (or a saved Dataverse view). Filter fsi_assessmentstatus = NotAssessed and fsi_severity ∈ {High, Critical} to surface what needs human eyes.

Step 2 — Assess

For each row, fill in the 7 admin-owned columns:

  • fsi_assessmentstatus → Reviewed / ImpactsAgents / NoImpact
  • fsi_assessment → narrative notes
  • fsi_assessedby → your UPN (auto-populate via Power Apps)
  • fsi_assesseddate → now
  • fsi_actionstaken → "Filed change log entry CR-1234"
  • fsi_impactsagents → boolean
  • fsi_notifiedon → if you informed downstream teams

Step 3 — Verify the trail

Tomorrow's sync re-runs against the same MC ID. Open the row again — your 7 columns are exactly what you typed. The Graph-owned fields (title, body, services) may have changed; that's expected.

Step 4 — Export evidence

Quarterly: run Export-MessageCenterEvidence.ps1 for the auditor. Output is hash-chained JSON; Test-EvidenceIntegrity.ps1 verifies the chain end-to-end.

Step 5 — React to Teams alerts

If a high/critical post lands, the adaptive card in your Teams channel links straight to the Dataverse row. One click → assessment.

Teams notification

Severity-gated. Only posts where fsi_severity matches one of the comma-separated levels in fsi_MCM_NotifySeverities (default high,critical) trigger an adaptive card.

Where

  • Team — fsi_MCM_TeamsTeamId
  • Channel — fsi_MCM_TeamsChannelId
  • Empty values = notification skipped (the sync still runs successfully).
  • Built by a Power Automate cloud flow you assemble manually (template payload in templates/teams-notification-card.json).

Card content

  • Title + severity badge
  • One-line summary
  • Affected services chips
  • Action required by date (red if < 7 days)
  • Two buttons: Open in Dataverse, Open in MAC
By design: the card never includes the full body. FSI customers do not want potentially confidential M365 admin commentary echoed into a wide-distribution Teams channel.

Operational guardrails — what's in the code

Built-in protections

  • Secret redaction — Write-McmRedacted scrubs Bearer tokens, Authorization headers, client_secret, access_token, refresh_token from every log line.
  • Retry with backoff — Invoke-McmRest honours Retry-After headers (H2/H3 parsing) on 429/5xx.
  • Token caching — refreshes ~5 minutes before expiry; cached per scope.
  • Idempotent upsert — alt-key based; safe to re-run.
  • SupportsShouldProcess — -WhatIf / -Confirm on the sync entry point.

Test coverage

  • Pester (PowerShell) — 57 tests across 4 files, all mock-based, hard-gated in CI.
    • Upsert.Tests.ps1 — 8 cases for the C1 invariant.
    • Common.Tests.ps1 — formatters + retry + token cache + redaction.
    • Sync.Tests.ps1 — orchestration counter math.
    • Guards.Tests.ps1 — guards every HTTP-using script through the helpers.
  • pytest (Python) — 13 tests covering schema script idempotency + key creation payload.
  • Lab smoke — Step 6 verifies C1 against live wires.

FAQ

Why Dataverse, not just SharePoint?

Need an alternate key + idempotent upsert + row-level audit + role-scoped security + Power Automate native binding. SharePoint's audit/security model doesn't meet FINRA 4511 in practice.

Can I use this in a multi-environment ALM pipeline?

Yes. The schema scripts and env-var scripts both honour --dry-run; wrap them in your standard Power Platform pipeline (sandbox → test → prod).

How does it handle Microsoft renaming a service in MAC?

fsi_services is Graph-owned, so it gets refreshed on the next sync. Your assessment narrative in fsi_assessment stays intact (it's admin-owned).

Government cloud / DoD?

v2.5.0 is commercial cloud only. Gov/DoD endpoints + sovereign Key Vault tier are tracked as future work.

What happens if Microsoft adds a new severity level?

The sync stores whatever Graph returns; you'll see the new value in fsi_severity. Add it to fsi_MCM_NotifySeverities if you want Teams alerts for it.

Can I attach the assessment to a Power BI dashboard?

Yes — Dataverse table is accessible via the standard Dataverse Power BI connector. Build whatever views/queries fit your governance KPIs.
