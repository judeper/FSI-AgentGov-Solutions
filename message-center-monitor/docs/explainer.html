Message Center Monitor

Daily-poll, supervised assessment, tamper-evident evidence — for AI agent platform-change risk in regulated Financial Services environments. This is the in-depth companion to the slide deck; everything is grounded in the actual repo source.

v2.5.0 Pillar 2 · Lifecycle & Operations Controls 2.3 · 2.10 Enterprise zone Live

Why this exists

Microsoft posts platform changes to the M365 Message Center every business day. A meaningful subset of those posts change how Copilot Studio agents — and the connectors, knowledge sources, and security posture they depend on — behave. In a regulated Financial Services environment, "we read the e-mail digest" is not an auditable supervisory practice.

What the regulators expect

  • FINRA Rule 3110 — the firm's supervisory system must address technology and platform changes that affect client communications and recordkeeping. Generic e-mail triage is not a supervisory system.
  • FINRA Rule 4511 — books and records must be retained in a non-rewriteable, non-erasable format. The assessment trail (who reviewed which Microsoft change, when, with what conclusion) is part of that record.
  • SEC Rule 17a-4 — evidence of supervisory review must be retained and made available on request.
  • SOX 302/404 — change-management controls over systems supporting financial reporting must be documented and operating effectively.
  • OCC Bulletin 2011-12 / Federal Reserve SR 11-7 — model risk management for AI/ML-driven decisions: changes to the underlying platform are changes to the model environment.

"We read the e-mails" satisfies none of these. A queryable, append-only assessment trail with role-based authorship and tamper-evident export does.

What goes wrong without this solution

  • The Message Center digest goes to a shared mailbox; nobody owns triage.
  • If anyone does assess a post, their notes live in Wiki / SharePoint / Teams — disconnected from the source post and not query-able as a corpus.
  • When the same post is republished by Microsoft (which happens often), the admin's prior assessment is invisible to whoever sees it next.
  • And the regression that motivated the v2.4.0 fix (the "C1" defect): a re-sync would silently overwrite admin assessments with the default NotAssessed status — the most damaging kind of bug because it produces a clean record with the wrong values.

What it does

Three pieces working together. None of them is novel by itself; the value is in the integration plus the strict ownership boundary.

1. Sync

A scheduled PowerShell entry point (Invoke-MessageCenterSync.ps1) pulls Message Center posts from Microsoft Graph, builds a Dataverse upsert payload, and writes via the table's alternate key. Idempotent and safe to re-run.

2. Assessment

Each row exposes 7 admin-owned columns (status, narrative, who, when, actions taken, agent-impact flag, notify date). Front it with a model-driven app, a Power Apps form, or even a Power Automate approval flow.

3. Notification + evidence

Severity-gated Teams card on high/critical posts. Quarterly hash-chained JSON evidence export with an integrity verifier for the auditor.

Architecture

Daily poll → managed-identity auth → idempotent upsert → admin assessment → Teams alert (severity-gated).

Components in detail

Microsoft Graph

Endpoint: https://graph.microsoft.com/v1.0/admin/serviceAnnouncement/messages. Required application permission: ServiceMessage.Read.All (admin consent required). The sync filters by lastModifiedDateTime ge X where X is "now − DaysBack".

Authentication

One of five modes — see Auth modes. The runner caches tokens by scope (Graph and Dataverse are separate scopes) and refreshes ~5 minutes before expiry.

Sync runner

scripts/governance/Invoke-MessageCenterSync.ps1 orchestrates the loop. It dot-sources scripts/governance/_Common.ps1, which provides:

  • Get-McmAccessToken — uniform token acquisition across all 5 auth modes (MSAL.PS-based)
  • Get-McmDvHeaders — cached Dataverse headers with proactive refresh
  • Invoke-McmRest — retry-aware REST wrapper that honours Retry-After
  • Format-McmODataLiteral — single-quote OData literal escape (defense against injection)
  • Format-McmODataDate — ISO-8601 round-trip Dataverse date formatter
  • Invoke-McmDvUpsertMessage — the C1-safe upsert (see below)
  • Write-McmRedacted — log helper that scrubs Bearer / client_secret / access_token

Dataverse

Custom table fsi_messagecenterlog with 21 columns (13 Graph-owned, 7 admin-owned, plus the system primary). The alternate key fsi_MessageCenterIdKey on fsi_messagecenterid enables idempotent upsert via PATCH .../fsi_messagecenterlogs(fsi_messagecenterid='MCxxxxx').

Notification

A Power Automate cloud flow (built per docs/flow-configuration.md — no exported flow JSON ships in the repo) watches for new/updated rows where fsi_severity is in fsi_MCM_NotifySeverities. It posts an adaptive card (template in templates/teams-notification-card.json) to the channel identified by fsi_MCM_TeamsTeamId + fsi_MCM_TeamsChannelId.

End-to-end flow

First PATCH attempts CREATE (If-None-Match: *); on 412 the row exists, so a second PATCH without the header and without admin columns merges only Graph-owned fields.

Numbered walkthrough

  1. Acquire token — the runner asks _Common.ps1 for a Graph token via the configured auth mode. Token is cached.
  2. Page Message Center — GET /admin/serviceAnnouncement/messages with $filter=lastModifiedDateTime ge {now − DaysBack}. The runner pages through @odata.nextLink until exhaustion.
  3. For each post — build record — map Graph fields to the 13 Graph-owned Dataverse columns. Never add an admin-owned column key to this hashtable.
  4. Acquire Dataverse token — distinct scope; cached separately.
  5. Try CREATE — PATCH .../fsi_messagecenterlogs(fsi_messagecenterid='MCxxxxx') with If-None-Match: *. Body = $Record (cloned) + fsi_assessmentstatus = NotAssessed. On 201 Created, the row is new and assessment defaults to NotAssessed.
  6. On 412 — UPDATE — the row already exists. The runner re-sends a PATCH with the original $Record (the un-cloned one — admin cols never present), no If-None-Match, and Dataverse merges only the Graph-owned fields.
  7. Counter math — increment NewRecords or UpdatedRecords accordingly.
  8. Severity gate — if fsi_severity matches one of the configured notify severities, the cloud flow's row-trigger fires and posts a Teams card.
  9. Emit summary — PSCustomObject with TotalSynced / NewRecords / UpdatedRecords / HighSeverityCount / CriticalCount / SyncTimestamp. Output as Table / JSON / Object per -OutputFormat.

What the helper guarantees

The contract of Invoke-McmDvUpsertMessage (from _Common.ps1) is intentionally narrow:

  • The caller passes a $Record hashtable that excludes all 7 admin columns. The helper enforces this by adding only fsi_assessmentstatus to a CLONE of $Record (used for create), and reusing the original verbatim for the update branch.
  • HTTP 201 → row created with fsi_assessmentstatus = NotAssessed.
  • HTTP 412 → row exists; second PATCH issued WITHOUT If-None-Match and WITHOUT admin columns.
  • HTTP 404 → alternate key not provisioned. Throws with an actionable hint pointing at create_mcm_dataverse_schema.py.

The C1 invariant explained

"C1" was the most damaging finding of the v2.4.0 council review. It is the kind of bug that produces clean records with the wrong values — the worst class for an audit trail.

What the bug was

In v2.3.0, the inline upsert in Invoke-MessageCenterSync.ps1 built one PATCH body per post and unconditionally included fsi_assessmentstatus = NotAssessed. On every sync — including re-syncs of posts that admins had already assessed — the picklist reset to NotAssessed. The other admin columns were not touched on update because they weren't in the payload, but the status flip alone was enough to invalidate the audit trail (and to confuse the assessment-status report, which uses fsi_assessmentstatus as its primary grouping).

What the fix is

v2.4.0 extracts the upsert into Invoke-McmDvUpsertMessage in _Common.ps1. Two key contract points:

  1. The function CLONES $Record before adding the assessment status default. The clone is used for the create payload only. The original $Record (which by contract never contains admin columns) is used verbatim for the update payload.
  2. The function uses If-None-Match: * to distinguish create from update. On 412 it issues a second PATCH without the header and without admin columns.

The result: it is structurally impossible for sync to write any of the 7 admin columns once the function compiles correctly.

How we know the fix works

  • Unit-level — tests/Upsert.Tests.ps1 mocks Dataverse and asserts, for 8 scenarios, that the JSON body of the update PATCH has zero set-intersection with the 7 admin column names.
  • Integration-level — lab/06_Invoke-LabSmokeTest.ps1 seeds an MC ID, lets sync land it, then back-dates fsi_lastupdated on the row to force the update path, then asserts byte-equality of all 7 admin columns before and after a second sync.
  • CI gate — Pester run is hard-gated in CI; a regression here is impossible to merge without the test failing.
Why the C1 invariant matters beyond this solution: any FSI governance solution that mixes machine-written and human-written columns on the same row needs an equivalent invariant. Use this implementation as a template for those.

Alternate key

The schema script creates fsi_MessageCenterIdKey on fsi_messagecenterid. This key enables the idempotent upsert URL pattern PATCH .../fsi_messagecenterlogs(fsi_messagecenterid='MCxxxxx') that the C1-safe upsert relies on. Key creation is async — the lab's 03_Deploy-Schema.ps1 polls until the key state is Active (up to ~15 minutes).

Pick the highest-trust mode the host supports. All three governance scripts accept -AuthMode.

Why managed identity is the default

Message Center sync runs every day, unattended. ClientSecret leaves a 24-month-rotating credential in Key Vault that must be audited, rotated, and explained to FSI Security. Managed identity has none of those obligations. WorkloadIdentity is the equivalent for hosted CI / pipeline runners that don't have a managed identity but can present an OIDC-issued federated token.

Note: managed identity requires MSAL.PS 4.37 or later. Older versions throw with an actionable upgrade hint.

  • Microsoft Entra app — application permission ServiceMessage.Read.All with admin consent.
  • Dataverse Application User — created by the lab's 04_New-AppUser.ps1. Production deploy creates it manually in Power Platform Admin Center. Assign a security role with create + read + write on fsi_messagecenterlog (or use the OOTB System Customizer in lower environments).

Installation

Three paths. Pick one. The lab dry-run is the recommended starting point even if you ultimately deploy via path 2 or 3 — it proves the pieces fit together end-to-end before you involve production change control.

Run the 8 numbered scripts under message-center-monitor/lab/. Bootstrap an entire non-prod deployment (app reg + KV + schema + app user + env vars), then run a 10-step smoke test that exercises the C1 invariant against live Dataverse. Hard non-prod safety guard: every mutating script refuses to run unless lab-config.json contains the literal acknowledgement string. See docs/lab-dry-run.md for the full runbook.

② Production deployment

Follow docs/setup-checklist.md:

  1. Create app registration in Microsoft Entra. Add ServiceMessage.Read.All application permission. Grant admin consent. (Use managed identity for the runner instead, if running on Azure.)
  2. (Skip if managed identity) Create Key Vault, generate client secret, store as MessageCenterClientSecret.
  3. Run the 3 Python schema scripts against your target Power Platform environment.
  4. Create the Dataverse Application User in Power Platform Admin Center; assign the security role you created in step 3.
  5. Set the 6 fsi_MCM_* env-var values for this environment.
  6. Build the Power Automate cloud flow per docs/flow-configuration.md (manual, no exported JSON ships in the repo). Use connection references so the flow is portable.
  7. Schedule the sync — Azure Automation runbook (recommended) or a "Recurrence" cloud flow that calls the PowerShell via Azure Container Instances / Functions.
  8. Watch the first sync and the first Teams notification land.

③ Pipeline-driven (advanced)

Wrap the Python schema scripts (which all support --dry-run) in your standard Power Platform pipeline. Deploy env vars + connection refs + flows via the standard Power Platform pipelines mechanism. Sync runner ships as a PowerShell module, callable from any host.

Day-to-day use

The supervised assessment workflow, from triage to evidence.

Step 1 — Triage

Open the model-driven app or your saved Dataverse view. Filter fsi_assessmentstatus = NotAssessed and fsi_severity ∈ {High, Critical} to surface what needs human eyes. (You can also subscribe to the Teams channel to be pushed the high/critical ones in real time.)

Step 2 — Assess

For each row, fill in the 7 admin-owned columns. The recommended Power Apps form binding:

  • fsi_assessmentstatus → option-set picker (NotAssessed / Reviewed / ImpactsAgents / NoImpact)
  • fsi_assessment → multiline text area (your narrative analysis — this is the FINRA / SOX evidence)
  • fsi_assessedby → auto-populate from User().Email in Power Apps
  • fsi_assesseddate → auto-populate from Now() on save
  • fsi_actionstaken → "Filed change log entry CR-1234" (cross-reference to your change-management system)
  • fsi_impactsagents → boolean toggle
  • fsi_notifiedon → set when you've informed downstream stakeholders (governance committee, risk, etc.)

Step 3 — Verify the trail

Tomorrow's scheduled sync will re-run against the same MC ID. Open the row again — your 7 columns are exactly what you typed. The Graph-owned fields (title, body, services) may have been updated by Microsoft; that's expected and correct.

Step 4 — Export evidence (quarterly)

Run scripts/governance/Export-MessageCenterEvidence.ps1 for the auditor. Output is hash-chained JSON; scripts/governance/Test-EvidenceIntegrity.ps1 verifies the chain end-to-end. See Evidence & integrity.

Step 5 — React to Teams alerts

If a high/critical post lands between scheduled triage windows, the adaptive card in your Teams channel links straight to the Dataverse row. One click → assessment.

Teams notification

Severity-gated. Built on Power Automate, not in the PowerShell runner — that keeps the auth surface narrow (the runner only needs Graph + Dataverse).

Trigger

The cloud flow you build per docs/flow-configuration.md uses a Dataverse "When a row is added, modified, or deleted" trigger on fsi_messagecenterlog. The trigger condition filters to rows where fsi_severity is in the comma-separated fsi_MCM_NotifySeverities env var (default high,critical).

Payload

Adaptive card template lives in templates/teams-notification-card.json. The flow substitutes the row's title, severity, summary, affected services, and action-required-by date. Two buttons:

  • Open in Dataverse — deep link to the row's form (uses fsi_MCM_DataverseUrl + entity logical name).
  • Open in MAC — deep link to the post on the Microsoft Admin Center.
By design: the card never includes the full body. FSI customers do not want potentially confidential M365 admin commentary echoed into a wide-distribution Teams channel.

If env vars are empty

Either of fsi_MCM_TeamsTeamId or fsi_MCM_TeamsChannelId being empty causes the flow's "Post adaptive card in chat or channel" action to no-op. The sync still completes successfully — notification is opt-in, not required.

Evidence & integrity

Quarterly export for FINRA 4511 / SEC 17a-4 / SOX records retention. Hash-chained so any post-export tampering is detectable.

How the export works

  • Export-MessageCenterEvidence.ps1 queries all rows for the requested time window, including all 7 admin columns.
  • Each row is canonicalised (ordered key set, ISO-8601 dates) and SHA-256 hashed.
  • The export file is a JSON document with: header (export time, range, signer UPN), an ordered array of row objects each carrying its row_hash, and a final chain_hash = SHA-256(prev_chain_hash || row_hash) accumulated over all rows.

How to verify it

Test-EvidenceIntegrity.ps1 consumes an export file and re-computes both row_hash for each row and the rolling chain_hash. Any mismatch produces a non-zero exit code with the offending row index.

What this is — and isn't

This is a tamper-evident record, not a tamper-proof one. An attacker with write access to the export file can rebuild the chain. For FINRA 4511 you should also ship the export to WORM storage (e.g., immutable Azure Blob with legal hold). The hash chain detects in-flight or post-storage tampering; WORM prevents the tampering from being permanent.

Operational guardrails

In the code

  • Secret redaction — Write-McmRedacted scrubs Bearer tokens, Authorization headers, client_secret, access_token, refresh_token from every log line.
  • Retry with backoff — Invoke-McmRest honours Retry-After headers (H2/H3 parsing, both delta-seconds and HTTP-date) on 429/5xx.
  • Token caching — refreshes ~5 minutes before expiry; cached per scope.
  • Idempotent upsert — alt-key based; safe to re-run any number of times.
  • SupportsShouldProcess — -WhatIf / -Confirm on the sync entry point.
  • Strict mode — every script runs Set-StrictMode -Version Latest + $ErrorActionPreference = 'Stop'.

In the lab harness

  • Non-prod ack string — every mutating script refuses unless lab-config.json contains the literal acknowledgement.
  • Owner-ACL secret handoff — secret passes from 01 → 02 via a gitignored file with restrictive ACLs (env-var handoff was unreliable across pwsh process boundaries).
  • Idempotent teardown — 99_Remove-LabDeployment.ps1 reads recorded state and removes only what the harness created.

FAQ

Why Dataverse, not SharePoint?

Need an alternate key + idempotent upsert + row-level audit + role-scoped security + Power Automate native binding. SharePoint's audit/security model doesn't meet FINRA 4511 in practice.

Multi-environment ALM?

Yes. The schema scripts and env-var scripts both honour --dry-run; wrap them in your standard Power Platform pipeline (sandbox → test → prod).

What if Microsoft renames a service?

fsi_services is Graph-owned, so it gets refreshed on the next sync. Your assessment narrative in fsi_assessment stays intact (it's admin-owned).

Government cloud / DoD?

v2.5.0 is commercial cloud only. Gov/DoD endpoints + sovereign Key Vault tier are tracked as future work.

What if Microsoft adds a new severity level?

The sync stores whatever Graph returns; you'll see the new value in fsi_severity. Add it to fsi_MCM_NotifySeverities if you want Teams alerts for it.

Power BI dashboard?

Yes — fsi_messagecenterlog is accessible via the standard Dataverse Power BI connector. Build whatever views fit your governance KPIs.

Can the assessment be done by an automated agent?

Yes — but only if your governance framework allows it. The C1 invariant doesn't care about who the writer is. If a Copilot Studio agent has a Dataverse connection with write access to the 7 admin columns, it can populate them. Document that delegation explicitly per your supervisory framework.

What about deletes?

Sync never deletes. Microsoft does not remove old MC posts; they just stop modifying them. If you need to purge for retention, do it via a separate scheduled job that respects your records-retention policy.
